# Okane

Personal-use clone of the Venezuelan app **Rial** (multi-currency personal finance: Bs/USD/USDT,
exchange rates, budgets, savings goals, receivables/payables, shopping lists). Built for the
repo owner's own use, not to be sold/distributed — local-first, no backend, no auth.

## Stack

- Expo Router (SDK 54) + NativeWind (Tailwind for RN). Dark theme only, no light mode toggle.
- **expo-sqlite + Drizzle ORM**, local-first. Chosen over a backend to avoid server costs, but
  designed since day one to be sync-friendly later (UUID PKs, soft-delete, consistent timestamps)
  so a future backend migration doesn't require reshaping the schema.
- `expo-glass-effect` + `expo-linear-gradient` are installed (real iOS 26 Liquid Glass +
  gradients) but currently **unused for money/amount cards** — see "Design decisions" below.

## Database (`db/`)

- `db/schema/*.ts` — 13 tables: currencies, exchange_rates, accounts, categories, transactions,
  budgets, savings_goals, goal_contributions, contacts, debts, debt_payments, shopping_lists,
  shopping_list_items. Only **currencies, accounts, transactions** have real UI built so far
  (see "What's implemented" below) — the rest of the schema exists but has no sc reens yet.
- `db/schema/_shared.ts` — `idCol()` (UUID text PK, generated with a plain-JS uuidv4, not
  `expo-crypto` — that package broke `drizzle-kit generate` because it pulls in `react-native`
  and esbuild chokes on it; don't reintroduce a native-module import inside `db/schema/*.ts`,
  since those files are evaluated by drizzle-kit under Node, not just by the app) and
  `syncCols()` (`createdAt`/`updatedAt`/`deletedAt`).
- `db/schema/relations.ts` — all Drizzle `relations()` calls are centralized here (not
  colocated per-table) specifically to avoid import cycles between e.g. `accounts.ts` and
  `transactions.ts`.
- **Money**: always integer minor units (`amountMinor`, e.g. céntimos), never `real`/float.
- **Exchange rates**: `exchange_rates` is append-only (never mutate a rate row), keyed by
  `(baseCurrencyId, quoteCurrencyId, rateType, effectiveAt)`. `rateType` is `bcv` | `parallel` |
  `manual`; when converting, the most recently recorded row (any `rateType`) wins — ties on
  `effectiveAt` fall back to `manual` > `parallel` > `bcv` (see `pickLatestUsdRate` in
  `db/queries/currencies.ts`). `rateScaled`/`rateScale` is fixed-point
  (quote-currency minor units per 1 base-currency major unit) to avoid float drift.
  `db/seed.ts` seeds **static placeholder rates** (VES→USD: bcv 700, parallel 800, manual 1000;
  USDT→USD 1:1) — these are not live/fetched, replace with a real rate-fetching feature later.
- **Balances**: `accounts.balanceMinor` is a cache **derived from `transactions`**, recomputed
  inside the same `db.transaction()` as any insert/update/delete that touches it — never set
  directly from the UI. Creating an account with an opening balance inserts a real `transactions`
  row (`entrySource: "manual"`, description "Saldo inicial"), not just a number (see
  `createAccount` in `db/queries/accounts.ts`).
- **Debts** (schema exists, no UI yet): creating a `debts` row immediately moves money — an
  `initialTransactionId` transaction is required, not optional — because lending/borrowing is
  itself a cash event by the user's explicit design decision, unlike a typical "IOU" model.
- **Budgets** (schema exists, no UI yet): meant to auto-renew monthly by copying the previous
  month's limit into a new row when opened, but that logic lives in the app layer — the schema
  only stores explicit `periodStart`/`periodEnd` ranges, nothing implicit about "current month".
- Migrations: `npx drizzle-kit generate` after any schema change, then the app applies them at
  boot via `useMigrations` in `app/_layout.tsx`. `db/migrations/migrations.js` is
  auto-regenerated by drizzle-kit — don't hand-edit it.

## What's implemented (UI)

Only **Home** (`app/(tabs)/index.tsx`), **Accounts CRUD** (`app/accounts/*`), and **Categories
CRUD** (`app/categories/*`) exist. Transactions, budgets, goals, debts, and shopping lists have
schema but no screens — don't assume a UI exists for them.

- **Every top-level route folder under `app/` needs a `<Stack.Screen name="..." options={{
headerShown: false }} />` entry in the root `app/_layout.tsx`'s `<Stack>`** (alongside
  `(tabs)`, `accounts`, `categories`). Each screen already draws its own header row (back arrow +
  title + action), so skipping this registration doesn't remove the native header — it just
  falls back to expo-router's default native-stack header, which stacks a second, OS-native
  header (different look on iOS vs Android, showing the previous route's folder name as the back
  label) on top of the custom one. This bit us once with `app/categories/*` — when adding a new
  top-level route folder, always add its `Stack.Screen` entry in the same change.
- **Accounts**: name vs label are two separate fields — `accounts.name` is always set from the
  institution picker (or the "Otro" custom-institution modal), never hand-typed;
  `accounts.label` is a genuinely optional free-text tag (e.g. "familiar") shown as a small pill
  next to the name in list rows. Don't collapse these back into one field.
- **Institution picker** (`components/accounts/InstitutionPickerSheet.tsx` +
  `lib/institutionCatalog.ts`): searchable bottom-sheet catalog of real banks/fintechs (Nacional =
  Venezuelan banks + "Efectivo"; Internacional = the specific list of apps the user asked for —
  see `lib/institutionCatalog.ts` for the current roster and domains). Icons are **real favicons**
  fetched via `https://www.google.com/s2/favicons?sz=...&domain=...` (see `lib/favicon.ts`), not
  bundled logo assets. "Otro" opens `AddCustomInstitutionSheet.tsx` to add any institution by
  name + logo URL — same favicon mechanism, `extractDomain()` parses whatever the user pastes.
  When extending the catalog, add entries to `NATIONAL_INSTITUTIONS`/`INTERNATIONAL_INSTITUTIONS`
  with a `domain` (for favicon) or `icon` (Ionicons glyph, only used for non-web entries like
  "Efectivo") — don't hardcode logo image assets.
- **IconBadge** (`components/ui/IconBadge.tsx`): renders either an Ionicons glyph tinted with
  `color` (translucent `${color}33` background) or, if `icon` is a URL (`http...`), an `<Image>`
  on a **solid** `color` background (not white) — the selected color swatch is meant to show
  through behind any logo, per explicit user design feedback.
- **Card vs GlassCard**: `components/ui/Card.tsx` (plain solid `bg-neutral-900`) is what's
  actually used for money/balance displays (Home balance, per-currency cards, Accounts "Balance
  total") — the user explicitly rejected the translucent glass look for these after seeing it
  looked like a mismatched gray box on the gradient background. `components/ui/GlassCard.tsx`
  (real `expo-glass-effect` wrapper) still exists and works but is currently unused — don't
  reach for it for amount/balance UI unless asked; it's fine for future non-money surfaces
  (modals, sheets) if that's ever wanted.
- **Dropdowns**: `components/ui/DropdownMenu.tsx` + `useDropdownAnchor()` is the generic pattern
  for anchored popovers (used for the accounts-list sort menu). It measures the trigger with
  `measureInWindow` — don't rebuild anchor positioning ad hoc elsewhere, reuse this.
- **Confirm sheets**: destructive actions use `components/ui/ConfirmSheet.tsx` (custom bottom
  sheet), not React Native's built-in `Alert.alert` — the user explicitly wants the app's own
  dark bottom-sheet style for confirmations, matching the rest of the UI.
- **Sorting accounts** by amount ("Mayor saldo") compares **USD-equivalent** value, not raw
  `balanceMinor` — comparing raw minor units across different currencies would be meaningless.
- Currency display order (Home's per-currency cards, Accounts filter chips) should follow
  `currencies.sortOrder` (VES=0, USD=1, USDT=2), not insertion/creation order.

## Known dev-environment gotchas (this machine)

- Adding any **native module** (e.g. `expo-sqlite`, `expo-glass-effect`) requires a full native
  rebuild (`npx expo run:ios`), not just a JS reload — `expo start` alone won't link it.
- CocoaPods on this machine needs `LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8` set or `pod install`
  fails with a Ruby/`UnicodeNormalize` error.
- After editing `babel.config.js` or `metro.config.js`, restart Metro with `--clear` — a plain
  reload keeps using the old in-memory transform cache and produces confusing errors (e.g. a
  `.sql` migration file getting parsed as JS).
- `.sql` migration files are loaded via `babel-plugin-inline-import` + `metro.config.js`'s
  `resolver.sourceExts.push('sql')` — both are required together, not just one.
- iOS Simulator tool taps: coordinates are in **points** (390×844 for iPhone 16e), not
  screenshot pixels (~918×1908) — divide screenshot-pixel coordinates by roughly the same scale
  factor before tapping, or better, reason in points directly from the layout code.
